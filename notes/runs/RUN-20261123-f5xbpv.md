## Notes
Each of 24 corpus cases parsed and re-serialized by three candidates: `icalendar` 0.17.17's
`Calendar`, its low-level `parser` (`read_calendar` and `Display`), and `calcard` 0.3.14.
Meaning is compared as the set of instances from 2026-12-01 to 2029-01-01 (start with zone
and UTC, duration, summary, description, location, status, transparency, class, organizer,
attendees with answers and roles, alarms, URL, attachments, categories), read by the
harness's own parser and expanded with `rrule` 0.14; raw properties are compared too.

What it showed (`out/crates/table.tsv`, `details.md`):
- `calcard`: meaning kept in all 24; the only rewrite is the order of RRULE parts
  (`BYDAY` before `BYMONTH`, `COUNT` moved), 6 of 24 outputs byte-identical.
- `icalendar` `Calendar`: meaning kept in all 24, but every write adds a random `UID` and
  a fresh `DTSTAMP` to each VTIMEZONE, each STANDARD and DAYLIGHT rule and each VALARM,
  which RFC 5545 does not allow there, and reorders properties: invalid and different on
  every write; 0 of 24 byte-identical.
- `icalendar` low-level parser: writes TEXT values unescaped, so an escaped newline in a
  DESCRIPTION became a real line break and the rest of it a bogus property (case 19), and
  `\,` `\;` `\\` lose their escapes elsewhere: unsafe for writing.

Before this run the corpus had commas unescaped in four SUMMARY values, which RFC 5545
forbids; the crates escaped them and the harness first counted that as a change. The
corpus was fixed and the harness now compares TEXT values unescaped (commit 22ad40b).

Not controlled by the script: the crate versions are pinned in `Cargo.lock`; nothing
else (no network, no clock dependence in the comparison).
